## 1. 문제 정의와 대상 사용자

### 문제
농인과 청인이 마주 앉아 대화할 때, 수어를 모르는 청인은 농인의 말을 이해하지 못한다. 농인은 청인의 말소리를 듣지 못한다. 필담은 느리고, 수어 통역사는 늘 곁에 있을 수 없다.

### 대상 사용자

| | 농인 (수어 사용자) | 청인 (음성 사용자) |
|---|---|---|
| 쓰는 언어 | 한국수어. 한국어 글은 읽을 수 있다고 가정한다(질문 Q12) | 한국어 음성 |
| 이 앱에서 하는 일 | 수어로 말하고, 자기 폰에서 청인의 말을 **자막으로 읽는다** | 자기 폰 카메라로 농인을 비추고, 화면에서 **번역 문장을 읽는다**. 평소처럼 말한다 |
| 폰의 역할 | 자막 화면만 담당. 카메라와 마이크는 쓰지 않는다 | 카메라(수어 인식)와 마이크(음성 인식)를 모두 담당 |
| 필요한 것 | 큰 글씨, 말하는 중인지 표시, 연결 상태 | 촬영 안내(상반신·양 어깨), 번역 중인지 표시, 확신도 낮은 단어 걸러내기 |

목업 4번과 5번 화면을 보면 카메라와 마이크는 모두 **청인 폰**에서 쓴다("카메라 사용 중 · 마이크 사용 중"). 무거운 계산(MediaPipe, 모델, 음성 인식)은 전부 청인 폰에서 돈다.

## 2. 목표와 성공 기준

### 목표
1. 아이폰 두 대로 연결부터 대화 종료까지 **인터넷 없이** 한 번의 대화를 끝까지 할 수 있다.
2. 시연 문장(최소 "사과 → 달다" → "사과가 달아요")이 청인 화면에 문장으로 나온다.
3. 청인의 말이 농인 폰에 실시간 자막으로 나온다.

### 성공 기준
숫자는 모두 **[목표]**이고 승인이 필요하다. 측정 방법을 같이 적었고, 각 마일스톤에서 실제로 잰 값으로 갱신한다.

| # | 항목 | 기준 [목표] | 측정 방법 |
|---|---|---|---|
| S1 | 단어 인식 지연: 수어 단어 끝 → 청인 화면에 단어 표시 | 중앙값 ≤ 0.8초 | 화면 녹화 후 프레임을 세어 측정. 구조상 단어 끝 판정에만 10프레임(약 0.33초@30fps) **[문서]**이 걸린다 |
| S2 | 문장 완성 지연: 마지막 단어 끝 → 문장 표시 | 중앙값 ≤ 2.0초 | 같은 방법. 설계상 45프레임(약 1.5초) 대기가 포함된다 **[문서]** |
| S3 | 모델 1회 추론 시간(청인 폰) | ≤ 30ms | 앱 안 계측 로그. 100회 평균 |
| S4 | 카메라 처리 속도(MediaPipe 포함) | ≥ 24fps 유지 | 앱 안 계측. 5분 평균 |
| S5 | 자막 지연: 청인이 말을 시작한 뒤 → 농인 폰에 첫 글자 | 중앙값 ≤ 1.0초 | 두 폰을 한 화면에 녹화해 프레임 세기 |
| S6 | 자막 정확도 | 시연 문장 20개 중 18개 이상 그대로 받아쓰기 | 정해 둔 문장을 읽고 결과 비교 |
| S7 | 연결 성공률 | 2m 거리 20회 시도 중 19회 이상 성공 | 찾기 → 요청 → 수락까지 수동 반복 |
| S8 | 연결 유지 | 15분 대화 중 끊김 0회 | 타이머를 켜고 연속 대화 |
| S9 | 연결까지 걸리는 시간 | 요청 → 대화 화면 진입 중앙값 ≤ 5초 | 수동 측정 |
| S10 | 전처리 일치 | Swift 출력이 Python `featurize`와 소수점 넷째 자리까지 같음(최대 절대오차 < 1e-4) | 자동 테스트(8절 M2) |
| S11 | 모델 일치 | 변환 모델의 1순위 단어가 PyTorch와 100% 같음 | 자동 테스트(M1) |
| S12 | 문장 생성 일치 | Swift 결과가 Python `compose_sentence`와 평가 문장 65개에서 100% 같음 | 자동 테스트(M3) |
| S13 | 배터리(청인 폰) | 30분 대화에 배터리 15% 이하 소모 | iOS 배터리 %를 처음과 끝에 기록 |
| S14 | 단어 인식 정확도(폰) | **기준을 먼저 재고 나서 정한다** | 시연용 단어 N개 × 10회. 웹캠 기준값은 6절 참고 |

S14를 미리 정하지 않는 이유: 노트북 웹캠에서 1순위 확신도 중앙값이 16%였다 **[실측, 2026-10-12]**. 폰에서 얼마나 나올지는 재 보기 전에는 모른다. M6에서 기준값을 잰 뒤 목표를 함께 정한다(질문 Q10).

## 3. 범위 / 범위 밖

### 범위
- iOS 앱 하나에서 역할 선택(농인/청인)
- 블루투스 등 근거리 통신으로 주변 사용자 찾기, 연결 요청·수락·거절, 대화 끝내기
- 청인 폰: 카메라 → MediaPipe Holistic → 전처리 → 모델 → 단어 → 문장, 화면 표시
- 청인 폰: 마이크 → 한국어 음성 인식 → 농인 폰으로 전송
- 농인 폰: 자막 표시(지난 문장 + 지금 말하는 중인 문장)
- 확신도 기준 미만 단어 버리기(기준값 설정 가능)
- 촬영 안내("상반신과 양 어깨가 보이게")
- 내 이름 수정(기기에만 저장)
- 오류 상태: 권한 거부, 연결 끊김, 손 미검출, 인식 실패

### 범위 밖
- 텍스트 → 수어 영상/아바타 생성
- 회원가입, 로그인, 서버에 대화 저장
- 모델 재학습과 파인튜닝
- 안드로이드 버전(이번 단계). 스마트글래스 단계와의 관계는 Q1~Q3
- 대화 기록 내보내기와 저장(대화를 끝내면 사라진다. 바꿀지는 Q13)
- 세 명 이상 그룹 대화

## 4. 사용자 흐름 (목업 5개 화면 기준)

```
[1 시작하기] ─농인으로 시작─┐
             └청인으로 시작─┴─> [2 주변 사용자 찾기] ─연결 요청 보냄─> (상대 수락 대기)
                                     │                                   │수락
                                     └─상대가 요청함─> [3 연결 요청] ─수락─┤
                                                         └거절─> [2]       ▼
                                                         농인: [4 농인 대화]  청인: [5 청인 대화]
                                                                       │대화 끝내기 / 끊김
                                                                       ▼
                                                                     [2] 또는 [1]
```

### 화면 1 — 시작하기
- **진입:** 앱 실행 시. 이전에 고른 역할을 기억할지는 Q14
- **문구:** "어떤 방식으로 대화할까요?" / **농인으로 시작** "상대방의 말을 자막으로 확인해요" / **청인으로 시작** "상대방의 수어를 한국어로 확인해요"
- **동작:** 버튼을 누르면 역할을 정하고 화면 2로 간다
- **권한:** 이 시점에 근거리 통신 권한을 요청한다. 카메라, 마이크, 음성 인식 권한은 청인 역할일 때만 요청한다(요청 시점은 5절 F1-3)

### 화면 2 — 주변 사용자 찾기
- **진입:** 화면 1에서 역할 선택, 또는 대화 종료 후
- **표시:** 상단 내 유형 배지(예: "청인"), 블루투스 애니메이션, "가까운 사용자를 찾고 있어요." / "연결할 상대방을 선택해 주세요.", "주변 사용자" 목록(이름, 유형 배지, **연결 요청** 버튼), "내 정보 · 내 이름"
- **동작:** 들어오면 자동으로 검색하고 내 기기도 알린다. **연결 요청**을 누르면 대기 상태가 된다(목업에 없음 → 5절 F2-4). 이름 행을 누르면 이름 수정
- **매칭 규칙:** **반대 역할만** 목록에 보여 준다(농인 ↔ 청인). 같은 역할끼리는 연결하지 않는다(Q15 답변)
- **오류 상태**
  - 근거리 통신 권한 거부: 목록 자리에 "주변 기기를 찾으려면 권한이 필요해요" + **설정 열기** 버튼
  - 블루투스 꺼짐: "블루투스를 켜 주세요" 안내
  - 30초 동안 아무도 없음: "주변에 사용자가 없어요. 상대방도 앱을 켜고 이 화면에 있어야 해요" (검색은 계속)
  - 상대가 거절: 토스트 "OO님이 요청을 거절했어요"
  - 요청 후 30초 동안 응답 없음: 대기를 취소하고 "응답이 없어요" 표시

### 화면 3 — 연결 요청
- **진입:** 화면 2에 있을 때 상대가 연결을 요청함
- **표시:** 상대 아바타, "OO님이 대화를 요청했어요.", 이름, 사용자 유형 배지, **수락하고 시작하기** / **거절하기**
- **동작:** 수락하면 연결을 맺고 역할에 따라 화면 4나 5로 간다. 거절하면 화면 2로 돌아간다
- **오류 상태:** 응답 전에 상대가 요청을 취소했거나 사라짐 → "요청이 취소됐어요" 표시 후 화면 2로

### 화면 4 — 농인 대화 화면 (농인 폰)
- **진입:** 연결 성공, 역할이 농인
- **표시:** 상단 "OO님과 대화" + "연결됨" 배지, "음성 자막" 영역
  - 완성된 문장: 회색 카드 + 시각(예: "오후 2:16"), 위에서 아래로 쌓인다
  - 지금 말하는 중인 문장: 파란 카드에 **크게** + "음성을 듣고 있어요"
  - 하단 **대화 끝내기**
- **동작:** 청인 폰에서 오는 부분 결과로 큰 카드를 계속 갱신한다. 문장이 끝나면 회색 카드로 내려간다. 새 문장이 오면 자동으로 아래로 스크롤한다
- **오류 상태**
  - 연결 끊김: 배지가 "연결 끊김"(빨강)으로 바뀌고 "다시 연결하는 중…"을 표시한다. 10초 안에 다시 붙지 않으면 "연결이 끊어졌어요" + **다시 찾기** 버튼
  - 상대 폰에서 음성 인식 오류: "상대방 기기에서 음성 인식이 멈췄어요" 표시(청인 폰이 상태로 알려 줌)
  - 상대가 대화 끝내기: "OO님이 대화를 끝냈어요" 후 화면 2로

### 화면 5 — 청인 대화 화면 (청인 폰)
- **진입:** 연결 성공, 역할이 청인
- **표시:** 상단 "OO님과 대화" + "연결됨", 카메라 미리보기(후면 카메라로 농인을 비춤), 미리보기 아래 띠 "카메라 사용 중 · 마이크 사용 중", "수어 번역" 영역에 번역 문장 + "수어를 번역하고 있어요", 하단 **대화 끝내기**
- **동작:** 들어오면 카메라와 음성 인식을 시작한다. 처음 몇 초는 어깨너비 보정이다(`realtime.py`의 보정 단계와 같음). 보정 중에는 "상반신과 양 어깨가 보이게 비춰 주세요"를 표시한다
- **오류 상태**
  - 카메라 권한 거부: 미리보기 자리에 "수어를 번역하려면 카메라 권한이 필요해요" + **설정 열기**. 음성 자막은 계속 동작한다
  - 마이크 또는 음성 인식 권한 거부: 띠에 "마이크 꺼짐" 표시, 농인 폰에도 상태를 보낸다. 수어 번역은 계속 동작한다
  - 사람 또는 어깨 미검출 2초 이상: "상반신과 양 어깨가 화면에 들어오게 해 주세요"
  - 손 미검출(사람은 보이는데 양손이 없음) 3초 이상: "손이 화면 안에 보이게 해 주세요"
  - 인식 실패(구간은 잡혔지만 확신도가 기준 미만): 단어를 버리고 작게 "다시 해 주세요" 표시. 버린 단어는 문장에 넣지 않는다
  - 연결 끊김: 화면 4와 같다

## 5. 기능 요구사항

우선순위: **필수** = 시연에 반드시 필요 · **있으면 좋음** = 시간이 남으면

### F1. 공통
| ID | 요구사항 | 우선순위 |
|---|---|---|
| F1-1 | 목업의 문구, 레이아웃, 색을 따른다. 기준색은 목업에서 뽑은 값: 주 버튼 파랑 ≈ `#285EE0`, 연한 파랑 배경 ≈ `#E0EEFC`, 회색 카드 ≈ `#F0F2F6`, 제목 글자 ≈ `#031035`, 대화 끝내기 빨강. 구현할 때 다시 정확히 뽑는다 | 필수 |
| F1-2 | 내 이름과 역할은 기기에만 저장한다 | 필수 |
| F1-3 | 권한은 그 기능이 필요한 순간에 요청한다(청인: 화면 5 진입 직전) | 필수 |

## 7. 기술 구조

### 7.1 전체 구조

```
청인 폰 (iPhone)                                               농인 폰 (iPhone)
┌──────────────────────────────────────────────────┐          ┌──────────────────────┐
│ AVCaptureSession(후면) ─> MediaPipe Holistic        │          │                      │
│   ─> frame89 ─> OneEuro ─> LiveNormalizer ─> energy │          │  화면 4: 음성 자막     │
│   ─> SegmentGate ─> featurize(64×356) ─> 모델       │  텍스트   │  (부분/완성 문장)      │
│   ─> 확신도 필터 ─> SentenceBuilder ─> 화면 5        │ ───────> │                      │
│                                                  │ 상태     │  (선택) 내 수어 번역    │
│ 마이크 ─> 온디바이스 STT ─> 부분/최종 자막 ──────────┼────────> │                      │
└──────────────────────────────────────────────────┘          └──────────────────────┘
```

Swift 코드는 세 덩어리로 나눈다.
- `SignCore`(Swift Package): 전처리, 세그멘테이션, 문장 생성. UI와 iOS 프레임워크에 의존하지 않아 **맥에서 `swift test`로 Python 기준값과 비교할 수 있다.**
- `SignInference`: MediaPipe와 모델 런타임 래퍼
- `App`: SwiftUI 화면, 연결, 음성 인식

Python 쪽 도구(테스트 데이터 생성, 모델 변환)는 이 폴더의 `tools/`에 둔다. 모델 저장소는 읽기만 하고 그 안에 파일을 만들지 않는다.

### 7.2 기술 결정

#### D1. 수어 인식을 어디서 돌릴 것인가

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 온디바이스 (청인 폰)** | 인터넷 필요 없음. 영상이 기기 밖으로 나가지 않음. 지연이 네트워크에 좌우되지 않음 | 모바일 변환과 Swift 전처리 이식이 필요. 폰 발열과 배터리 |
| B. 서버(노트북 등) | Python 코드를 그대로 씀(이식 없음) | 영상이나 랜드마크를 네트워크로 보내야 함. 시연장 와이파이에 좌우됨. 개인정보 문제. 범위 밖인 "서버"가 생김 |
| C. 혼합(MediaPipe는 폰, 모델과 문장은 서버) | 이식량이 줄어듦 | B의 네트워크 문제가 그대로 남음 |

**추천: A.** 모델이 5MB이고 파라미터가 126만 개라 폰에서 충분히 돌 것으로 본다(S3 ≤ 30ms는 **[추정]**, M1/M6에서 실측). MediaPipe Holistic은 iOS용 공식 가이드가 있다(`MediaPipeTasksVision`, `HolisticLandmarker`, `RunningMode.video/.liveStream`) **[문서]**. 오프라인과 개인정보 요구도 A만 만족한다.

#### D2. 모델 변환 형식

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. ONNX Runtime (iOS용)** | 같은 `.onnx` 파일을 PC(`onnxruntime` Python), iOS, **안드로이드(글래스 단계)**에서 그대로 씀. PC에서 PyTorch와 바로 비교 가능. `TransformerEncoder` 내보내기가 잘 알려진 경로 | 앱 크기가 몇 MB 늘어남 **[추정]**. Apple 뉴럴 엔진은 CoreML 실행 제공자를 따로 켜야 씀 |
| B. Core ML (`coremltools`) | iOS 기본. 뉴럴 엔진 사용. 앱 크기 부담 없음 | iOS 전용이라 글래스 단계에서 다시 변환해야 함. PC 비교는 macOS에서만 가능. `nn.TransformerEncoder`의 eval 빠른 경로 연산이 변환에서 막힐 수 있어 우회가 필요할 수 있음 **[추정]** |
| C. ExecuTorch | PyTorch 공식 모바일 런타임, iOS·안드로이드 모두 지원 | 설정이 가장 복잡함. 이 규모 모델에는 과함 |
| D. LiteRT(TFLite, `ai-edge-torch` 변환) | 안드로이드와 공유 가능 | PyTorch → TFLite 변환이 셋 중 가장 손이 많이 감. iOS 쪽 문서가 상대적으로 적음 |

**추천: A (ONNX Runtime).** 모델이 작아서 뉴럴 엔진이 꼭 필요하지 않고, 하나의 파일을 PC·iOS·안드로이드에서 같이 쓰는 이점이 크다. M1에서 실제 지연이 S3를 넘으면 B(Core ML)로 바꾼다.

**변환 후 확인 방법 (M1)**
1. 체크포인트를 불러 `eval()` 상태로 `torch.onnx.export`(입력 `(1, 64, 356)`)
2. 저장소의 실제 클립과 웹캠 녹화로 만든 `featurize` 출력 N개(예: 200개)를 PyTorch와 `onnxruntime`에 똑같이 넣는다
3. 통과 조건: **1순위 단어가 100% 같고**, logit 최대 절대오차 < 1e-3
4. 같은 입력과 기대 logit을 테스트 데이터로 저장해, iOS 앱 안 테스트(XCTest, 실기기)에서도 같은 조건으로 확인한다

#### D3. 전처리 이식 (`PROMPT.md` 4절 1~6단계 → Swift)

| 단계 | Python | Swift 이식 메모 |
|---|---|---|
| 1 | MediaPipe Holistic | iOS `HolisticLandmarker`. Python과 같은 옵션(`min_pose_detection_confidence=0.5`, `min_hand_landmarks_confidence=0.3`) |
| 2 | `holistic_result_to_frame89` | 인덱스 표 그대로 이식. 정규화 좌표 × 이미지 폭·높이 = 픽셀 좌표 |
| 3 | `LiveNormalizer` | 그대로 이식. `DEGENERATE_SCALE_PX = 5.0` |
| 4 | `OneEuroFilter` | 그대로 이식(`min_cutoff=1.2, beta=0.3, d_cutoff=1.0`). `dt`는 프레임 타임스탬프로 계산 |
| 5 | `hand_energy`, `SegmentGate` | 그대로 이식(`start 0.06, end 0.03, end_hold 10, min 6, max 90`) |
| 6 | `featurize` | `center_and_scale`(클립 중앙값 대체), `clip(-20, 20)`, `np.interp` 선형 보간, 속도 차분 |

**선택지**
- **A. Swift로 직접 이식 + Python 기준 테스트 (추천)**: 계산량이 작아(최대 90×89×2) 일반 Swift 배열로 충분하다. Python과 같은 순서로 계산하고 `Float32`/`Double` 정밀도를 Python에 맞춘다(numpy 기본은 float64, 입력은 float32)
- B. 전처리까지 ONNX 그래프에 넣기: 이식 코드는 줄지만 상태가 있는 단계(OneEuro, Gate)는 그래프로 못 넣어 결국 반은 Swift로 써야 한다

**확인 방법 (M2):** Python 스크립트(`tools/make_fixtures.py`)가 저장소 코드를 import해서 (a) 원시 frame89 시퀀스, (b) 단계별 출력(필터 후, 정규화 후, 에너지, 게이트 판정, `featurize` 결과)을 JSON/NPY로 저장한다. Swift `swift test`가 같은 입력을 넣어 **최대 절대오차 < 1e-4**인지 확인한다(S10). MediaPipe 단계(1)는 iOS와 Python의 빌드가 달라 비트 단위로는 같을 수 없으므로, 같은 영상 프레임에서 랜드마크 차이를 **따로 재서 보고한다**(통과 기준은 Q17).

**주의할 차이**
- **프레임 수 기준 값:** `end_hold 10`, `sentence_end_hold 45`는 약 30fps를 가정한다. 폰 fps가 다르면 체감 시간이 바뀐다. 처음에는 Python과 똑같이 프레임 기준으로 이식하고(일치 테스트를 위해), M6에서 fps를 잰 뒤 시간 기준으로 바꿀지 정한다
- **좌우와 방향:** `realtime.py`는 영상을 뒤집지 않는다. 청인 폰은 후면 카메라라 뒤집히지 않은 영상이 들어온다(Python 웹캠과 같은 조건). 세로 화면 방향은 MediaPipe에 넘길 때 올바르게 지정해야 하며, 왼손·오른손이 바뀌지 않는지 M5에서 확인한다
- **얼굴 34점:** 매핑이 근사치라 **[문서]** 저장소도 `--no-face` 비교를 권한다. 앱에도 같은 스위치를 둔다(기본값 Q8)

#### D4. 문장 생성 (`kslx/sentence.py`)

**조사한 사실**
- `sentence.py`는 kiwi를 두 군데에서 쓴다. (1) 단어 **하나씩** 품사를 분석하는 `kiwi.tokenize(gloss)`, (2) 형태소 열을 문장으로 합치는 `kiwi.join()`(받침에 맞춘 조사 이형태, 어미 활용, 과거형 축약, 띄어쓰기)
- (1)은 입력이 **닫힌 어휘 1200단어**라서 결과를 PC에서 미리 계산해 표로 넣을 수 있다
- (2)에서 활용이 필요한 술어는 어휘 중 '다'로 끝나는 121개와 `HADA` 사전의 명사들이다. 형태는 (현재/과거) × (합쇼체/해요체) 4가지뿐이라 이것도 미리 계산할 수 있다. 나머지는 명사 + 조사(은/는, 이/가, 을/를, 과/와, 으로/로, 에, 에서)와 서술격 '이다'인데, 받침 규칙으로 정해진다
- Kiwi 본체는 C++이고 C API(`capi.h`)가 있다. 다른 언어 바인딩(Rust, R, Flutter)이 이 C API를 감싼다 **[문서]**. iOS 공식 빌드는 찾지 못했다. 직접 크로스 컴파일하면 될 것으로 보이지만 해 본 사람의 기록이 없고, 형태소 모델 파일 크기도 확인하지 못했다

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 미리 계산한 표 + 규칙 Swift 이식** | 완전 오프라인. 앱이 가벼움. 결과가 정해져 있어 테스트하기 쉬움 | 어휘를 늘리면 표를 다시 만들어야 함(PC 스크립트 한 번). kiwi.join의 띄어쓰기와 이형태 규칙을 Swift로 맞춰야 함 |
| B. Kiwi C++를 iOS용으로 빌드해 그대로 호출 | Python과 결과가 같을 가능성이 가장 큼. 어휘 확장에 강함 | 크로스 컴파일 검증이 안 됨. 모델 파일만큼 앱이 커짐(크기 미확인). 빌드 문제로 일정 위험 |
| C. 서버(PC)에서 Python 호출 | 코드 그대로 | 오프라인 요구 위반. 시연장 네트워크 위험 |

**추천: A.** 확인 방법(M3): (1) `eval_sentence.py`의 평가 문장 65개(개발 40 + 나중 25)를 Swift에 넣어 **Python 결과와 같은지** 비교한다(정답과 같은지가 아니라, Python과 같은지가 기준. S12). (2) 어휘에서 무작위로 고른 단어 조합 1,000개를 Python과 Swift에 똑같이 넣어 다른 결과를 모두 목록으로 낸다. 표가 감당 못 하는 경우가 많으면 B로 바꾼다.

#### D5. 음성 인식 (STT)

| 선택지 | 한국어 | 오프라인 | 지연 / 특징 |
|---|---|---|---|
| **A. `SpeechAnalyzer` + `SpeechTranscriber` (iOS 26+)** | 지원 언어에 한국어 포함 **[문서, 2차 자료. 실기기에서 `supportedLocales`로 확인 필요]** | 온디바이스. 모델은 시스템이 내려받아 관리 | 긴 대화용으로 설계됨. 부분 결과(volatile) 제공. 시간 제한 없음 **[문서]** |
| B. `SFSpeechRecognizer` + `requiresOnDeviceRecognition` | 한국어 지원 | 한국어 온디바이스 가능 여부는 기기에서 확인 필요 **[추정]** | 오래된 API. 요청당 시간 제한이 있어 계속 재시작해야 함 **[추정]** |
| C. WhisperKit(Whisper Core ML) | 한국어 지원 | 완전 오프라인 | 모델이 수백 MB, 부분 결과 지연이 큼 **[추정]**. 카메라 처리와 계산 자원을 다툼 |

**추천: A**, 쓸 수 없는 기기는 B로 대체. 결과적으로 **최소 iOS 26**이 된다. 팀 아이폰의 iOS 버전을 확인해야 한다(Q6). M7에서 한국어 지원 여부, 첫 다운로드 필요 여부, 지연(S5)을 직접 잰다.

#### D6. 두 폰 연결 방식

주고받는 것: 텍스트(초당 최대 5회 정도의 부분 자막, 수십~수백 바이트)와 상태. 대역폭은 문제가 아니고 **찾기·연결의 안정성**이 중요하다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. MultipeerConnectivity (Apple)** | 아이폰끼리 찾기 → 초대 → 수락 흐름이 화면 2·3과 그대로 맞음. 블루투스와 기기 간 와이파이를 자동으로 고름. 암호화 지원. 구현량이 가장 적음 | **아이폰끼리만** 됨(안드로이드·글래스와 연결 불가). 오래된 API라 가끔 연결이 불안정하다는 보고가 있음 **[추정]** |
| B. Google Nearby Connections (Swift) | 안드로이드와 연결 가능하다고 공식 문서에 적혀 있음 **[문서]** | iOS용 설치 경로와 성숙도가 불분명함. 2024년 관리자 답변에 iOS↔안드로이드 BLE 찾기 문제 언급 **[문서]** |
| C. CoreBluetooth(BLE) 직접 구현 | 어떤 플랫폼과도 연결 가능. 의존성 없음 | 찾기, 연결, 메시지 쪼개기, 재연결을 전부 직접 만들어야 함. 일정 위험이 가장 큼 |

**추천: A**, 단 연결 코드는 `PeerTransport` 프로토콜 뒤에 숨겨서 글래스 단계에 B나 C로 바꿀 수 있게 한다. 이 추천은 **두 폰이 모두 아이폰**이라는 전제다. 한쪽이 안드로이드일 수 있으면 B를 먼저 검증해야 한다(Q2). 화면 문구 "블루투스로 …"는 A도 블루투스를 쓰므로 그대로 둔다.

#### D7. 앱 구조

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. Swift + SwiftUI (네이티브)** | MediaPipe, 카메라, 음성 인식, MultipeerConnectivity를 모두 공식 API로 바로 씀. 디버깅이 쉬움 | 글래스(안드로이드) 단계에서 UI를 다시 만들어야 함 |
| B. Kotlin Multiplatform(공통 로직) + SwiftUI | 전처리와 문장 생성을 한 번만 써서 iOS·안드로이드가 공유 | 빌드 설정이 복잡해지고 일정이 늘어남. 카메라와 MediaPipe는 어차피 플랫폼별로 써야 함 |
| C. Flutter / React Native | UI 공유 | 카메라 프레임 → MediaPipe → 모델 경로가 전부 네이티브 플러그인이라 이점이 작고 성능 위험이 큼 |

**추천: A.** 졸업작품 일정(11~12월 글래스 단계)을 생각하면 iOS를 빨리 안정시키는 것이 우선이다. 공유가 필요한 로직(전처리·문장 생성)은 `SignCore`로 분리하고 Python 기준 테스트 데이터를 공용으로 두면, 안드로이드 이식 때도 같은 테스트 데이터로 확인할 수 있다. 빌드 환경: Xcode 27.0, macOS 26.6.2 **[실측]**. MediaPipe는 Swift Package Manager로 설치한다 **[문서]**.

## 11. 화요일(11/3) 시연 범위

남은 기간이 6일 정도라서 9절 마일스톤을 줄인다. 목표는 **아이폰(청인)과 맥의 시뮬레이터(농인)로 "사과 → 달다" → "사과가 달아요"가 청인 화면에 나오고, 청인의 말이 농인 폰에 자막으로 뜨는 것**이다.

### 시연에 넣는 것
- 화면 1~5 (목업 문구·색 기준)
- 연결: 찾기, 요청, 수락, 거절, 대화 끝내기
- 청인 폰: 카메라 → MediaPipe → 전처리 → 모델 → 확신도 0.5 필터 → 해요체 문장
- 청인 폰: 한국어 온디바이스 음성 인식 → 농인 폰 자막
- 촬영 안내와 보정 단계, 개발자 화면(확률, fps)
- 전처리·모델의 Python 일치 테스트: 맥에서 자동으로 돌아가고 시간이 적게 든다. 숨은 계산 실수를 막기 위해 유지한다

### 화요일 이후로 미루는 것
- 대화 기록 저장(F1-6), 농인 쪽 번역 보기(F3-4), 청인 쪽 자기 말 자막(F5-3)
- 자동 재연결(F2-5), 다이내믹 타입·다크 모드, 수동 녹화 모드
- 성공 기준 전체 측정 보고서(M10), 배터리 30분 측정
- 문장 생성의 무작위 1,000개 비교(평가 문장 65개 비교는 한다)
